# 双机视频延迟波动分析与测试计划

日期：2026-09-29。

关联文档：[摄像头到 FFplay 端到端流程与排障说明](摄像头到FFplay端到端流程与排障说明-20260929.md)。

## 1. 现象和当前判断

用户观察到：两机距离越远，视频显示延迟总体越高；距离相同时，延迟仍然时大时小。

目前没有同步的无线质量、收发速率和分阶段时间戳记录，因此本文是待验证的原因分析，不是已完成的根因定论，也不包含本次新执行的性能测试结果。

优先怀疑两类因素叠加：

1. 无线链路质量下降引起有效带宽下降、重试、排队和到达抖动。
2. 当前 YUV 文件导出、目录轮询及 FFplay 播放流程增加额外等待，甚至补播历史帧。

不能仅凭距离规律认定解包错误或 GCC 失效。stride 花屏修复解决的是像素排列问题，不等于延迟问题也已解决。

## 2. 屏幕上看到的是整条链路的延迟

```text
摄像头曝光/采集等待
  → 输入转换与视频帧适配
  → 编码等待和编码
  → pacing、系统及无线设备中的发送排队
  → 无线网络传输
  → 接收缓冲、重组、解码
  → 按 stride 导出 YUV 文件
  → Python 扫描、读取、保存、显示队列
  → 管道、FFplay 缓冲与呈现
  → WSLg / 屏幕显示
```

概念上，总延迟是上述各段等待和处理时间之和。实际测量必须针对同一帧，并明确时间点，避免重复计入同一段等待。

`Notify frame decoded` 只能说明帧走到了接收解码环节，不代表该帧已经显示。RTT、解码反馈延迟也不等于摄像头到屏幕的端到端延迟。

## 3. 距离增大为何可能提高延迟

### 3.1 主要不是电磁波传播时间

实验室尺度多出几十米，传播时间变化远不足以解释肉眼可见的视频延迟。更可能的链路是：

```text
距离、遮挡或天线条件改变
→ 接收信号质量下降
→ 无线速率降低、链路层重试增加
→ 可供视频使用的有效传输能力下降
→ 等待发送的时间增加
→ 包更晚、更不均匀地到达
```

这只是符合现象的假设，必须结合实际拓扑和数据检验。端到端网络延迟需要考虑整个路径，而不只是无线传播段。参见 [Cisco 无线低延迟架构说明](https://www.cisco.com/c/en/us/products/collateral/wireless/arch-end-to-end-low-latency-wireless-networks.pdf)。

### 3.2 测量到热点的距离，不只测两机间距

同一热点下的典型路径是：

```text
发送电脑 → 手机热点/AP → 接收电脑
```

任一段无线链路变差都可能成为瓶颈。测试应分别记录发送端到热点、接收端到热点的距离，记录遮挡、频段、热点位置及设备朝向。若使用的是 Wi-Fi Direct 或其他拓扑，应先确认实际路径，不能套用上述假设。

### 3.3 GCC 有反馈和调整过程

网络能力突然下降时，编码器可能暂时仍按原速率产生数据。反馈返回并促使 GCC 调整之前，数据可能已在发送端或无线设备中排队。

即使 GCC 随后降低发送负载，已经积压的数据仍需要发送或丢弃。GCC 不能直接清空热点内部队列，也不会管理接收端 YUV 文件、Python 和 FFplay 缓存。

所以，出现延迟上升和恢复过程不等于 GCC 没起作用；看到 `BW est` 日志也不足以证明其弱网性能已经通过验收。需要联合观察估计带宽、实际发送速率、反馈和延迟，并排查外部码率覆盖。

## 4. 距离不变时，哪些环节仍会变化

| 环节 | 变化来源 | 可能表现 |
| --- | --- | --- |
| 摄像头 | 自动曝光、采集缓冲、USB 传输与调度 | 输入帧间隔不稳定 |
| 编码 | 画面运动、复杂场景、较大关键帧、计算资源竞争 | 编码耗时或短时数据量增加 |
| 无线网络 | 同频干扰、其他设备争用、遮挡、天线朝向、重试 | 到达抖动和发送排队 |
| 发送控制 | 可用能力变化与反馈调整的时间差 | 队列先增长、后消退 |
| 接收重组/缓冲 | 等待迟到包、必要的重传、依赖帧或关键帧 | 暂停、丢帧或恢复时跳跃 |
| 解码和导出 | CPU/GPU 调度、磁盘负载、容器和 WSL 运行状态 | 帧交付和文件发布变慢 |
| 显示 | 扫描历史文件、队列、管道阻塞、播放时序 | 已接收的帧仍延迟显示 |

WebRTC 有到达抖动估计与解码调度逻辑，网络抖动可能转化为接收侧等待。上游源码仅用于说明机制，不能代替对本项目具体分支的核查：[WebRTC 视频缓冲控制源码](https://webrtc.googlesource.com/src/+/3f152c4ed7e0877aff508609c09692212453ef3e/video/video_stream_buffer_controller.cc)。

无线链路层重试如果最终成功，上层未必体现为 RTP 丢包。因此，“丢包率低”不能排除无线链路已经带来明显的等待。

## 5. 当前显示脚本的已知风险

以下行为来自仓库 [camera_external_recorder.py](../../scripts/camera_external_recorder.py)，不是推测；它们对本次延迟的具体贡献尚未量化。

### 5.1 固定 15 fps 播放，没有原始采集时间戳

当前操作命令常用 `--fps 15`，脚本将其传给 FFplay 作为 rawvideo 的名义帧率。发送端示例是 `--fps 30`，实际采集、编码和解码帧率还可能不同。

这不代表延迟一定持续翻倍，因为脚本队列会尝试丢帧；但输入节奏与播放时间基准并不自动一致，可能出现等待、跳帧及不正确的时间线。

FFplay 有自身同步和丢帧机制，但无法恢复输入已经没有携带的采集时间戳。[FFplay 官方文档](https://www.ffmpeg.org/ffplay.html)

不能仅将 15 改为 30 就宣称根治。应先测实际帧率，最终让预览使用正确的时间信息或明确的最新帧呈现策略。

### 5.2 容量为 2 的队列只限制一层

```text
磁盘文件 → Python 扫描/读取/保存 → 显示队列 → 写线程 → 管道 → FFplay
                                      ↑
                               仅此队列容量为 2
```

其他环节仍可等待。脚本还会遍历整个目录、按文件名数字排序，并在提交显示前将帧写入连续 raw 文件。

启动时 `last_key=-1`，不会区分旧帧和本轮新帧。所以反复启动后显示固定旧片段，不是当前网络延迟的可靠测量。

### 5.3 同步落盘与重复保存

修复版在帧回调中同步导出文件；Python 随后读取，并再写入一份连续 raw。磁盘等待可能影响帧交付和显示提交。

960×540 I420 每帧为 777600 字节。实际达到 30 帧/秒时：

- 单份原始帧写入约 23.3 MB/s，十进制单位。
- 两份保存约 46.7 MB/s，另有读取、扫描和日志开销。

这不是磁盘已成为瓶颈的证据，只说明该路径需要纳入测量。目录文件越来越多，扫描和排序的负担也可能增加。

### 5.4 序号和超时带来的误判

文件名取自 RTP 序号，并非永远递增的独立帧编号。回绕或重连后序号变小，原脚本可能跳过新文件，造成停更或超时退出。

`--duration` 从脚本启动开始计时；`--idle-timeout` 在已经读到帧后才生效。显示脚本退出不代表 rx 已停止，rx 有帧也不代表播放器仍运行。

## 6. 优先开展的三个对照实验

全部使用真实网络，不配置 tc。保持现有 GCC 路径，不在尚未分层测量前盲目调整其参数。

### 实验一：近 → 远 → 近，分离距离和运行时间

固定热点、摄像头画面、分辨率和实验参数，在近处、远处、返回近处分别观察相同时间，并重复。记录设备位置和测试顺序。

原因：如果一直开着程序边走远，距离增加的同时，运行时间、目录规模和缓存也可能增加。

判读线索：

- 返回近处后延迟恢复：支持无线链路因素。
- 返回近处后仍长时间落后：检查残留队列、历史补播及程序状态。

再做各距离独立启动、相同观测时长的对照。每轮必须确认预览不在播放历史帧，避免把不同初始状态放在一起比较。上述现象都不是单次实验即可定论。

### 实验二：同步记录 RTT 与可见视频延迟

传输时低频 ping 对端，同时测摄像头到屏幕的延迟；记录空闲和传输期间的网络状态。不要用高频探测或吞吐压测额外压满链路。

| 观察 | 优先怀疑方向 |
| --- | --- |
| RTT 和画面延迟一起增加 | 网络排队或无线质量下降 |
| RTT 较稳定，画面越来越落后 | 编码、接收缓冲、导出、显示链路 |
| RTT 已恢复，画面仍明显落后 | 残留缓存、播放时间线或其他处理延迟 |

ping 是小包往返测量，不是视频单向传输测量；ping 正常不能完全排除媒体路径问题。记录实际媒体所用的接口/候选路径，避免 VPN 或路由差异造成错误比较。

### 实验三：接收端先测三段时间

为同一帧关联如下事件：

```text
A：解码帧进入导出回调
B：YUV 文件成功写完并发布
C：Python 读到该完整帧
D：Python 将该帧提交显示队列
```

使用同一时间域的单调时钟；若 C++、Python 和容器取时方式不同，先验证时间基准可比较。使用独立帧编号，处理 RTP 序号回绕，不只用文件名做长期关联。

- `B−A`：导出开销，包含同步文件写入等待。
- `C−B`：文件发现和读取延迟。
- `D−C`：脚本处理、保存等开销。
- D 以后还包括队列、管道及播放器呈现，不能把 D 当成屏幕显示时刻。

这部分需要增加诊断记录，当前尚未实施。跨机采集到解码的精确测量还需要时钟同步和误差说明。

## 7. 端到端延迟如何观察

可以先用可见计时器或可重复的亮灭事件测试。尽可能把真实事件与接收画面记录在同一个观测时间基准中；若使用两台电脑各自的时钟比较，必须先校时并记录误差。

不要把按固定帧率生成的 MP4 时长当作实际传输时间。也不要把 `LIVE_FRAMES_SUBMITTED` 当作真正显示帧数。

每个位置建议保留延迟中位数、较高分位数（如 P95）和明显卡顿事件，而不是只报一次最小值。缺少足够样本时，明确标为初步观察。

建议记录表：

| 轮次/位置 | 两端到 AP 距离及遮挡 | 运行时长 | 无线信号/协商速率 | RTT/丢包 | 实际发送/解码 fps | 可见延迟 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 近处 | 待填 | 待填 | 待填 | 待填 | 待填 | 待填 | 是否有旧帧 |
| 远处 | 待填 | 待填 | 待填 | 待填 | 待填 | 待填 | 是否移动镜头 |
| 返回近处 | 待填 | 待填 | 待填 | 待填 | 待填 | 待填 | 恢复耗时 |

其中无线协商速率不是视频可用吞吐量；码率也必须区分编码目标、估计带宽和实际发送字节统计。

## 8. 后续优化顺序

1. 确认挂载、帧导出、真实格式和播放器正常，排除已经遇到的非延迟故障。
2. 做近远近对照，避免把运行时间与距离混为一谈。
3. 测量接收端导出、扫描和提交开销。
4. 将预览与录像分离：预览优先最新完整帧，不补播历史；录像按独立策略保存。
5. 为接口增加时间戳、宽高和独立帧编号，完善动态分辨率及重连处理。
6. 在显示端等待已知且受控之后，再评价 GCC 的真实弱网适应表现。

目前不建议直接认定“需要换拥塞控制算法”或“只加 FFplay 低延迟参数就能解决”。若要进行参数或结构修改，应分别做前后对照，避免同时改变多个因素。

## 9. 总结

**距离可能通过无线质量影响网络延迟；接收缓冲和当前文件式显示链路又可能进一步放大或延长等待。等距离下的波动可以来自网络，也可以来自编码、磁盘及播放器。**

现在应先把“解码前的延迟”和“解码后的显示延迟”拆开。只有排除了补播、播放时序和本机积压，才能公平评估 WebRTC/GCC 在弱网中的表现。
