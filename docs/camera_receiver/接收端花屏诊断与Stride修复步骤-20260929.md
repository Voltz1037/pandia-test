用途：提供给持有新版摄像头 WebRTC 源码的同学，在不破坏现有信令兼容性的前提下修复接收端 YUV 导出。

## 1. 结论和验证边界

双机已经完成 RTP 接收、完整帧重组、解码和非空帧文件输出，但显示出现周期性横条、绿色条纹和斜向错位。

**当前证据强烈指向解码后的 I420 导出忽略实际行跨度（stride），不是优先修改 RTP 解包。** 仍需在真正的导出位置记录宽高及三个 stride，并通过修复后的单帧验证闭环。

本文是诊断与修复指南，不代表补丁已经应用、编译或验证通过。本机目前只有仓库二进制，没有与它匹配的完整新版源码。不要照着示例覆盖整个 Conductor 或 OnFrame。

目标二进制：`bin/peerconnection_camera`。

诊断时 SHA256：

```text
3de169e3da871b34d065880a133a4beae736866e31bbe069902d193c60211fbf
```

新版程序包含摄像头采集和信令分帧修改。修复必须基于这份程序对应的源码，不能换回旧公共分支的整套程序。

## 2. 已观察到的证据

### 2.1 文件有数据，不等于像素排列正确

接收日志出现 `Rtp packet received`、`Frame received`、`Notify frame decoded`。某次检查得到 1388 条解码通知和 1388 个非空帧文件；后续独立运行生成了 4815 帧，再次检查累计目录中达到 5026 帧。这些是不同时间的快照，不是同一统计窗口。

文件长度均为：

```text
777600 = 960 × 540 × 1.5
```

字节数符合名义 960×540 I420，但不能单独证明宽高或像素位置正确。

从本机 `pandia-camera-live-HIvaz0N9/frames/received_41187.yuv` 按 960×540 I420 离线转换 PNG，同样出现与 ffplay 截图一致的花屏。因此异常不局限于 ffplay 窗口或 WSLg 显示。

### 2.2 行跨度统计证据

对 saved Y 平面和 U 平面计算不同字节间隔的平均绝对差。自然画面相邻行通常较相似，结果如下，数值越低代表越相似：

| 样本 | Y 间隔 960 | Y 间隔 1024 | U 间隔 480 | U 间隔 512 |
| --- | ---: | ---: | ---: | ---: |
| received_41187.yuv | 28.9588 | 1.0558 | 17.1110 | 0.3950 |
| received_53208.yuv | 21.3703 | 0.9749 | 16.8230 | 0.3908 |

这与原始内存的 Y 行跨度为 1024、色度行跨度为 512，而导出文件被解释为紧凑 960/480 的情况高度一致。统计是诊断依据，不是运行时 metadata；V 平面的实际 stride 也必须读取，不直接推定或硬编码。

对上述同校验值二进制的 `cricket::VideoRenderer::OnFrame` 做只读反汇编检查，也发现了按平面宽高整块 memcpy 的导出路径，而非逐行 stride 拷贝。但还需对照源码确认实际生成文件的调用路径。

### 2.3 输出失败日志需另外核对

某次检查发现 `Failed to open the dumping file` 数量与解码和现存文件数量均为 1388。磁盘、inode、文件句柄都未耗尽，且实际已有文件。

不能因此说所有导出都失败，也不能直接把提示认定为误报。需搜索全部输出位置，核对是否有多个导出分支、另一个错误路径或其他逻辑问题；打印实际失败文件名及错误原因。

### 2.4 已区分的其他问题

- 先前任务栏有图标但窗口不可见，伴随 `WARN: COPY MODE`，对应 WSLg 共享内存初始化异常；重启后 `use_gfxredir=1`，测试图案恢复。该问题与当前像素花屏不同。
- 重启播放器继续使用旧目录，会重播已有帧；没有新帧或达到时限后脚本退出。这与 stride 花屏也是两件事。

## 3. 为什么忽略 stride 会花屏

假设一行有效宽度为 960，实际内存行距为 1024：

```text
第 0 行：960 字节有效像素 + 64 字节对齐填充
第 1 行：960 字节有效像素 + 64 字节对齐填充
...
```

连续复制 `960 × height` 字节，会把填充混入图像并遗漏尾部有效数据。播放器按每行 960 字节解释时，逐行产生错位。色度平面同类错误可能产生绿条。

不能仅将 ffplay 的宽度改成 1024：错误文件的各平面边界和尾部数据可能已经损坏。应从解码 buffer 正确导出新的帧。

## 4. 源码侧修复步骤（持有新版源码的同学执行）

### 4.1 定位源码和所有导出位置

对方报告记录的源码位置为 `~/Workspace/webrtc-camera-src`。先确认实际目录，再执行：

```bash
  'received_|Failed to open the dumping file|Dump to|DataY\(|DataU\(|DataV\(' \
  --glob '*.h' --glob '*.cc' \

```

没有 rg 时可用：

```bash
git grep -n -E \
  'received_|Failed to open the dumping file|Dump to|DataY\(|DataU\(|DataV\(' \
  -- '*.h' '*.cc'
```

请将命中处完整函数、调用路径和实际输出文件名写回仓库。确认真正生成 `/dump/received_*.yuv` 的位置，不只根据类名猜测。

修改前备份确切文件，保留当前未提交修改。不要通过 git reset 或整文件覆盖抹掉摄像头、信令、dummy audio、remote renderer 空指针等现有修复。

### 4.2 获取明确的 I420 buffer，记录布局

在实际导出函数中使用如下逻辑；示例中的 `frame` 需对应真实解码帧对象：

```cpp
auto i420 = frame.video_frame_buffer()->ToI420();
if (!i420) {
  std::fprintf(stderr, "I420 export: conversion failed\n");
  return;
}
```

在首帧、尺寸或 stride 变化时打印，不建议长期每帧刷日志：

```cpp
std::fprintf(
    stderr,
    "I420 export: width=%d height=%d strideY=%d strideU=%d strideV=%d\n",
    i420->width(), i420->height(),
    i420->StrideY(), i420->StrideU(), i420->StrideV());
```

真实日志是最终依据。不得硬编码 stride=1024/512。

### 4.3 核心改动：逐行导出三个平面

按项目风格加入所需头文件：

```cpp
#include <cstddef>
#include <cstdint>
#include <cstdio>
#include <fstream>
```

辅助函数示例，可放在相应类内或适当作用域：

```cpp
static bool WritePlane(std::ofstream& out,
                       const uint8_t* data,
                       int stride,
                       int row_bytes,
                       int rows) {
  if (!data || stride < row_bytes || row_bytes <= 0 || rows <= 0)
    return false;

  for (int row = 0; row < rows; ++row) {
    const uint8_t* source =
        data + static_cast<std::ptrdiff_t>(row) * stride;
    out.write(reinterpret_cast<const char*>(source), row_bytes);
    if (!out)
      return false;
  }
  return true;
}
```

以下示例假设 `out` 已成功以二进制模式打开临时文件。它替换整块 memcpy / write 部分，不替换整个 OnFrame：

```cpp
const int width = i420->width();
const int height = i420->height();
const int chroma_width = (width + 1) / 2;
const int chroma_height = (height + 1) / 2;

bool ok =
    WritePlane(out, i420->DataY(), i420->StrideY(), width, height) &&
    WritePlane(out, i420->DataU(), i420->StrideU(),
               chroma_width, chroma_height) &&
    WritePlane(out, i420->DataV(), i420->StrideV(),
               chroma_width, chroma_height);

out.close();
if (!ok || !out) {
  std::fprintf(stderr, "I420 export: frame write failed\n");
  return;
}
```

保留本函数其他必要行为，例如帧转发。若实际导出函数不是 void 返回类型，按其类型调整错误处理。移除被替代且不再使用的原缓冲区分配，避免内存泄漏。

### 4.4 写完后再发布帧文件

建议同目录先写 `received_12345.yuv.tmp`，成功关闭后再 rename 为 `received_12345.yuv`。检查 rename 返回值，并打印失败路径及系统错误。

现有 Python 脚本只匹配 `received_<数字>.yuv`，不会读取 `.tmp`。临时文件与最终文件必须处于同一文件系统，才能利用原子重命名避免消费者读到半帧。

短时修复验收先保留原有帧 ID 命名。RTP 序号回绕、重连后重复命名等是下一阶段问题，不要据此宣称文件接口已适合长期运行。

## 6. 不在本次花屏修复中混改的事项

- 不修改 RTP 解包、ICE 或信令。
- 不通过关闭 GCC、强设网络码率来掩盖像素布局错误。
- 不直接把 ffplay 宽度从 960 改成 1024 作为修复。
- 不把旧 FIFO 补丁整文件覆盖到新版源码。
- 不把能响应明暗变化视为画面正确、低延迟通过。

当前外部脚本仍存在磁盘扫描、逐帧写盘、固定 15 fps、旧帧补播、序号回绕等限制。它生成的 4815 帧 MP4 在 15 fps 下为 321 秒，这是人为时间基准，不是实测网络传输时长。

花屏修复通过后，再分离预览与录像：预览优先最新帧、限制积压、保留时间戳；最后测量实际采集到显示延迟。队列只有两帧不代表 ffplay 和管道没有其他缓冲。
