# 双机实时显示方案统一与待修改项

日期：2026-09-29
用途：统一 `docs/camera_receiver` 新版摄像头联调资料与 `docs/receiver_preview` 的接收端 FIFO 显示资料，避免 Sender/Receiver 使用不兼容版本。

## 1. 先给结论

当前最重要的修改不是摄像头或网络，而是统一二进制和信令版本。

| 程序 | 信令 | 摄像头 | FIFO 显示 | 当前用途 |
| --- | --- | --- | --- | --- |
| `bin/peerconnection_camera` | 新版单行 JSON + 换行分帧 | 支持 `--path camera` | 没有内置 FIFO 显示 | 当前双机摄像头测试主方案 |
| `peerconnection_client_headless_ffplay_v2` | 原信令版本 | 不是摄像头主程序 | 支持 Y4M FIFO | 旧显示补丁记录，不能直接配新版 Sender |

因此：

1. 现在先统一使用仓库的 `bin/peerconnection_camera`；
2. 不要把新版摄像头 Sender 与旧的 `peerconnection_client_headless_ffplay_v2` 直接配对；
3. 如果要保留 FIFO 显示，必须把显示补丁合并到新版单行 JSON 源码后重新编译。

## 2. 本次日志暴露的问题

新版 Sender 与旧 Receiver 配合时，Sender 出现：

```text
Received 1 bytes from peer
Received 1378 bytes from peer
Received 3989 bytes from peer
```

这不是正常的单条 JSON 消息。新版协议要求每条消息为一行 JSON，并以 `\n` 结束。旧 Receiver 返回的 Answer/Candidate 被拆成多个片段后，ICE/DTLS 无法建立，最终结果是：

```text
Finish encoding: 0
SendPacketToNetwork: 0
Rtp packet received: 0
Frame received: 0
```

`Test-NetConnection ... -Port 9999` 只证明 TCP 信令连通，不证明 RTP/UDP 媒体连通。

## 3. 我们这边需要统一的配置

### 3.1 Sender

使用摄像头模式：

```bash
/home/cjq/Workspace/Pandia/bin/peerconnection_camera \
  --server 172.20.10.2 \
  --port 9999 \
  --width 640 \
  --fps 30 \
  --path camera
```

不要使用旧测试视频流程中的：

```text
--width 720 --fps 25
```

除非明确运行的是旧文件 Sender。

### 3.2 Receiver

当前建议先使用同一个新 binary：

```bash
docker run -d \
  --name pandia-receiver \
  --network host \
  --gpus all \
  -v "$HOME/Workspace/Pandia/bin/peerconnection_camera:/opt/pandia-bin/peerconnection_camera:ro" \
  -v "$HOME/Workspace/Pandia/bin/nvidia-libs:/opt/nvidia-libs:ro" \
  -e LD_LIBRARY_PATH=/opt/nvidia-libs \
  --entrypoint /opt/pandia-bin/peerconnection_camera \
  johnson163/pandia_receiver:latest \
  --receiving_only \
  --port 9999
```

校验值：

```text

```

### 3.3 显示和录制

当前推荐外部方案：

```text
Receiver --dump_path
  -> camera_external_recorder.py
  -> FFplay
  -> MP4
```

当前 `peerconnection_camera` 的实际输出为：

```text
960 x 540
YUV420p
```

所以外部脚本使用：

```text
--width 960 --height 540
```

如果改用 FIFO v2，则输出是：

```text
640 x 360 Y4M
```

两条显示路径不要混用，也不要让两个 ffplay 同时读取同一个 FIFO。

## 4. 对方文档中需要补充或修正的地方

### 4.1 旧 v2 命令必须标注为“不可与新版 Sender 直接配对”

`docs/receiver_preview/接收端实时显示阶段工作总结与复测指南.md` 已经提到这一点，后续启动命令中还应增加醒目标记：

```text
WARNING: v2 是旧信令版本，不能直接与 bin/peerconnection_camera 配对。
```

### 4.2 旧 v2 的输入参数与摄像头模式不同

该文档中的：

```text
--width 720 --fps 25
```

属于旧的测试视频 Sender 配置。摄像头模式应统一为：

```text
--width 640 --fps 30 --path camera
```

### 4.3 显示尺寸要明确区分

- 新版外部录制：`960x540`；
- 旧版 FIFO v2：`640x360`；
- Sender 摄像头采集：`640x480`，WebRTC 内部会做视频适配。

不能把 640x360 的 Y4M 流直接按 960x540 解码，也不能把 960x540 的 dump 帧按 640x360 播放。

### 4.4 `receiver-ffplay` 补丁文件应一起归档

文档引用了：

```text
receiver-ffplay/ffplay_video_renderer.h
receiver-ffplay/apply_receiver_preview.py
receiver-ffplay/固定显示尺寸升级步骤.md
```

但当前仓库中还没有这些文件。若要让其他人复现 FIFO 显示，需要把这些文件和实际 v2 binary 的 SHA256、编译命令一起提交。

## 5. 推荐的下一阶段顺序

### 阶段 A：先验证媒体链路

只运行：

```text
bin/peerconnection_camera Sender
bin/peerconnection_camera Receiver
```

通过标准：

```text
Sender: Finish encoding / SendPacketToNetwork
Receiver: Rtp packet received / Frame received / Notify frame decoded
```

### 阶段 B：验证外部显示和 MP4

使用：

```text
--dump_path + camera_external_recorder.py
```

通过标准：

```text
FFplay 窗口持续显示
生成 MP4
FFprobe 能读到视频帧
```

### 阶段 C：移植 FIFO v2 显示

完成以下修改后再测试：

1. 将 `ffplay_video_renderer.h` 合并到新版 `conductor`；
2. 保留单行 JSON + `\n` 的信令 framing；
3. 保留 `remote_renderer_->SetDumpPath()` 修复；
4. 重新编译新的 Receiver；
5. 只启动一个 ffplay；
6. 验证分辨率变化时窗口不退出。

## 6. 最终判定

只有以下日志同时出现，才算双机实时视频通过：

```text
Sender:
Connected to the receiver
Camera source result: ok
Finish encoding
SendPacketToNetwork

Receiver:
Sender connected
Rtp packet received
Frame received
DecodeAndMaybeDispatchEncodedFrame
Notify frame decoded
```

在这些条件满足前，不应把 FIFO 显示或旧 v2 结果写成“新版双机实时显示已经通过”。
