# 摄像头到 FFplay：端到端流程与排障说明

日期：2026-09-29。适用：曹家齐侧摄像头 Sender → 徐健博侧 Docker Receiver → WSL FFplay。

本文依据仓库 `2581636` 的说明、stride 修复补丁、`camera_external_recorder.py` 实际代码及徐健博侧联调记录整理。目的是解释每一步的数据、组件职责和验收方法，不把历史成功等同于当前仍在运行。

## 1. 一句话说明

**摄像头提供实时画面，Sender 中的 WebRTC 编码并发送，Receiver 中的 WebRTC 收包、重组、解码；我们增加的导出代码将解码帧保存为紧凑 I420 文件，Python 脚本读取文件，通过标准输入管道交给 FFplay 显示。**

本轮不是管理员的 `env_emulator_offline.py` 实验，不依赖它的 ONNX 模型或 trace 数据；也不是旧的 Y4M FIFO 补丁。

## 2. 完整数据流

```text
发送电脑：Windows + WSL
  USB 摄像头
    ↓ USB 转接到 WSL，V4L2 设备 /dev/videoX
  peerconnection_camera --path camera
    ↓ 摄像头 MJPEG 数据 → 采集模块解码/转换为视频帧
  WebRTC 视频源与轨道
    ↓ 帧适配 → 视频编码（当前工程使用 H.264 路径，具体编码器以日志为准）
  编码帧 → RTP 分包 → pacing 调度 → 网络发送
    │
    │ 双机实际网络，媒体通常走协商出的 UDP 路径
    ↓
接收电脑：Windows + WSL + Docker Desktop
  Docker 内 peerconnection_camera_stridefix --receiving_only
    ↓ WebRTC 接收媒体包 → 重排/缓冲/帧重组 → 视频解码
  解码后的 VideoFrame
    ↓ VideoRenderer::OnFrame → ToI420 → 按 stride 逐行导出
  received_<first_rtp_sequence>.yuv.tmp
    ↓ 写完并关闭后，原子重命名
  received_<first_rtp_sequence>.yuv
    ↓ bind mount：容器和 WSL 看见同一批文件
  WSL：camera_external_recorder.py
    ├─ 连续保存到 received.yuv → 测试结束后 FFmpeg 编码 received.mp4
    └─ 有界队列 → 写线程 → FFplay 标准输入 pipe:0
                               ↓ 按 yuv420p / 宽高 / 名义帧率解释数据
                             WSLg → Windows 上的显示窗口

另有两条双向控制链路：
  Sender ← TCP 9999 信令：Offer / Answer / ICE candidates → Receiver
  Sender ← WebRTC 接收反馈、RTCP 等控制信息 ← Receiver
```

“单向视频”只表示图像从摄像头端发到地面端；建立连接和拥塞控制仍需要反向通信，不能把反向网络全部屏蔽。

## 3. 各部分究竟负责什么

| 部分 | 输入 → 输出 | 不负责什么 |
| --- | --- | --- |
| USB / V4L2 | 摄像头数据 → WSL 可采集的视频数据 | 不负责跨电脑传输 |
| Sender 内 WebRTC | 视频帧 → 编码视频的媒体包 | 不生成地面站显示窗口 |
| 信令 TCP 9999 | 协商消息 → 双方建立 PeerConnection 所需信息 | 不是把全部视频字节直接灌入 9999 |
| Receiver 内 WebRTC | 网络媒体包 → 解码视频帧 | 原 headless 程序不自动弹出 GUI |
| stridefix 导出 | 带内存行距的帧 → 紧凑 I420 文件 | 不负责网络带宽控制 |
| Docker bind mount | 将容器目录映射到 WSL 目录 | 不是重新传输或转码视频 |
| 外部 Python 脚本 | 单帧文件 → 连续 raw 数据、FFplay stdin | 不做 RTP 解包或 H.264 解码 |
| FFplay | 原始像素 → 图形窗口 | 当前不参与 WebRTC 信令、ICE 或 RTP 接收 |
| FFmpeg 录像步骤 | 连续 raw 数据 → MP4 | 当前在测试收集结束后执行，不是实时传输的必要条件 |

Receiver 镜像仍然需要：它提供程序运行时及依赖。通过 `--entrypoint` 和只读挂载使用修复版程序，不代表旧镜像默认程序也被修改了。

## 4. 摄像头采集和发送

### 4.1 摄像头先进入 WSL

对方现有方案将 USB 摄像头通过 usbipd 接入 WSL，再由 V4L2 采集。设备号、BUSID 要以发送电脑现场为准，不能照搬另一台电脑的值。

仓库记录的输入为 MJPEG，采集日志显示过 640×480。这里的 MJPEG 是摄像头到采集模块的输入格式，**不表示网络发送的仍是 MJPEG**。进入 WebRTC 编码流程前需要得到可处理的视频帧。

若摄像头被预览软件或旧 Sender 占用，先关闭对应进程。不要在 Sender 采集时同时开另一个摄像头测试程序。

### 4.2 采集帧率、编码帧率和显示帧率是不同的量

Sender 当前示例：

```bash
/home/cjq/Workspace/Pandia/bin/peerconnection_camera \
  --server 172.20.10.2 --port 9999 \
  --width 640 --fps 30 --path camera
```

这是发送电脑的路径，接收地址换网后必须重新核实。`--fps 30` 不是对最终解码或显示 30 fps 的保证，实际还受采集、适配、编码和网络影响。

发送端曾记录 640×480，而接收导出实际为 960×540。说明不能只根据摄像头参数设置 FFplay。中间具体是哪一处配置决定该尺寸，需要发送端完整源码/配置进一步定位；本文不把 960×540 说成 WebRTC 必然的默认输出。

### 4.3 信令与媒体分别工作

当前定制程序用 TCP 9999 交换信令，双方信令按兼容的消息边界处理。历史上的旧 FIFO binary 与新版 camera binary 不能直接混用。

信令完成后，WebRTC 用 ICE 选择可用连接路径。STUN 用于辅助发现地址，TURN 可以中继；它们不是专门把 Docker 网桥接在一起的工具。同一可达网络可能不需要外部 STUN/TURN，但 TCP 连通不等于媒体路径已连通。参见 [WebRTC 官方 Peer Connections 说明](https://webrtc.org/getting-started/peer-connections)。

当前部署命令没有启动 STUN 容器，也没有执行 tc；这不能替代对整台机器是否存在其他网络规则的检查。

### 4.4 GCC 在哪里

GCC 属于 WebRTC 传输控制链路：利用接收反馈估计可用发送能力，影响发送侧码率分配和 pacing 等行为。它不负责清理 YUV 文件，也不负责 FFplay 的队列。

当前方向是使用 WebRTC 原生拥塞控制，不接入 Pandia 的外部 FPS/bitrate Action 控制器。但“出现 BW est 日志”或“能够传输”不足以证明弱网自适应性能已经验收；需要记录实际码率、估计值、反馈和延迟随真实网络变化的情况，并确认没有外部覆盖。

## 5. 接收端已经做了哪些“解包”工作

接收端 WebRTC 不是只把 UDP 包存起来。它负责处理媒体传输、按 RTP 序列/时间信息重组编码帧、进行必要的缓冲和反馈，再将编码帧交给解码器。

可以按以下证据判断进度：

```text
Rtp packet received        收到相关 RTP 包
Frame received             已有编码帧重组结果
Notify frame decoded       出现解码完成通知
I420 export / YUV 文件增长  解码帧成功进入导出接口
```

因此 `Notify frame decoded` 已经说明流程走过收包、重组和解码；但它不保证后面的磁盘写入、Python 读取或窗口显示成功。

## 6. 修复后的 YUV 导出接口

### 6.1 帧回调

远端视频轨绑定 sink，收到解码帧后调用 `VideoRenderer::OnFrame`。相关代码在：

```text
examples/peerconnection_headless/client/conductor.h
```

本轮使用 `--dump_path` 文件导出分支；补丁中虽有 `media_bridge_` 分支，但不能把本轮文件显示说成已启用模型桥接。

### 6.2 为什么旧代码会花屏

实际帧内存布局曾为：

```text
width=960 height=540 strideY=1024 strideU=512 strideV=512
```

`width` 是有效像素宽度，`stride` 是内存中相邻两行起点的距离。Y 平面每行有效 960 字节，但下一行从 1024 字节之后开始。

旧代码把 `width * height` 字节整块复制，混入行尾填充并丢失部分有效内容；FFplay 按紧凑行距解释时就出现横条、绿带和错位。文件总大小即使正确，像素排列也可能是错的。

修复版先 `ToI420()`，再按 Y、U、V 顺序逐行写：

```text
Y：从 DataY + row * StrideY 读取 width 字节
U：从 DataU + row * StrideU 读取 ceil(width / 2) 字节
V：从 DataV + row * StrideV 读取 ceil(width / 2) 字节
```

960×540 的紧凑 I420 单帧长度为：

```text
960 × 540 + 480 × 270 + 480 × 270 = 777600 字节
```

一般尺寸应按 `W*H + 2*ceil(W/2)*ceil(H/2)` 计算；目前 Python 脚本使用 `W*H*3//2`，应限定偶数宽高。

### 6.3 原子文件发布

先写 `.yuv.tmp`，关闭文件并检查成功后，再重命名为 `.yuv`。Python 只匹配最终 `.yuv`，减少读取半帧的风险。

另一处旧的 `/app/media/res_video/` 导出代码也修复了 stride，且只在该目录可写时启用。这与本轮 `--dump_path` 是两个导出位置，不要混淆错误来源。

修复没有解决所有实时性问题：文件仍以 RTP 序号命名，长时间运行可能回绕或覆盖；Python 的排序逻辑也还没有支持该情况。

## 7. 容器中的帧怎样到达 WSL

徐健博侧最近一次恢复使用的映射如下：

| 位置 | 路径 |
| --- | --- |
| 容器名 | `pandia-stridefix-rx-v2` |
| 容器程序 | `/opt/pandia-bin/peerconnection_camera_stridefix` |
| 容器导出目录 | `/pandia-output/frames` |
| WSL 对应目录 | `/home/luo_k/pandia-stridefix-LIoZAovC/frames` |

挂载的是父目录 `/home/luo_k/pandia-stridefix-LIoZAovC` → `/pandia-output`，不是在容器中再拷贝一份文件。

曾经的故障是运行中删除并重建了挂载目录，容器仍引用旧目录，出现：

```text
I420 export: failed to open /dump/received_....yuv.tmp, errno=2
```

接着 `docker restart` 又因 Docker Desktop 内部旧 bind-mount 路径不存在而失败。最终保留旧容器，使用有效父目录挂载创建 `pandia-stridefix-rx-v2`，确认可写及监听 9999。

**不要在容器运行期间删除其挂载源目录。** 缓存清理应在停止相关读写后针对明确的旧帧文件进行；重启容器不等于清除旧帧，重新创建同名目录也不保证旧挂载自动恢复。

## 8. Python 如何将帧交给 FFplay

实现文件：[camera_external_recorder.py](../../scripts/camera_external_recorder.py)。

当前脚本的真实行为是：

1. 大约每 30 ms 扫描一次输入目录。
2. 匹配 `received_<数字>.yuv`，要求文件大小等于指定宽高对应的帧长度。
3. 将文件名里的数字排序，只处理大于本次 `last_key` 的帧。
4. 将帧写入连续 `received.yuv`，并提交到显示队列。
5. 显示队列容量为 2，满时尝试丢掉最旧的排队帧。
6. 后台线程把帧数据写入 FFplay 的标准输入并 flush。

脚本创建的 FFplay 命令等价于：

```bash
ffplay -loglevel warning \
  -f rawvideo -pixel_format yuv420p \
  -video_size 960x540 -framerate 15 \
  -window_title "Pandia Receiver Live" -i pipe:0
```

这是对管道输入的说明，不要单独运行后期待它自行寻找帧文件。`pipe:0` 的数据由 Python 写入。

rawvideo 不包含自动识别所需的完整格式信息，所以必须明确像素格式、宽高和帧率；这些参数错了会出现错位或错误时序。参见 [FFmpeg rawvideo 文档](https://ffmpeg.org/ffmpeg-formats.html#rawvideo)。

这里 FFplay 读的是已解码的 I420，不再做网络 H.264 解码，也不处理 TCP 9999。通过 WSLg 才能把 Linux 图形窗口显示到 Windows 桌面。

## 9. 为什么“实时收到”不一定“实时显示”

### 9.1 原脚本会读旧文件

每次启动 `last_key=-1`，并不区分本次新帧与目录里的历史帧。因此重启后播放几秒并退出，可能是在补播旧文件。

容量为 2 的队列只限制 Python 中这一层排队，不能消除磁盘扫描历史、管道和 FFplay 内部缓冲。当前实现还不是严格的“只显示最新帧”。

### 9.2 15 fps 是人为设置的播放时间基准

脚本不携带摄像头采集时间戳。它把连续原始帧交给 FFplay，按 `--fps 15` 解释；实际输入快慢和网络抖动不会自动转换成正确的采集时间线。

因此 MP4 时长主要由保存帧数 / 设置帧率决定，不能据此反推真实采集时长或端到端延迟。`LIVE_FRAMES_SUBMITTED` 是提交数，不是屏幕实际呈现帧数。

### 9.3 超时从脚本启动开始算

`--duration 120` 是整个脚本运行时限，不是收到第一帧之后的 120 秒。没有任何帧，也会达到时限后结束。

`--idle-timeout 10` 只在已经读到过帧后生效。曾出现显示脚本结束并报告 0 帧，随后 Receiver 才收到视频的情况：rx 仍运行不代表 FFplay 仍运行。

### 9.4 当前不是常驻产品级预览器

尚待改进：预览与录像分离、仅处理新完成帧、最新帧优先、独立递增帧编号、携带时间戳和宽高、处理动态分辨率、完善播放器退出和线程停止。

原脚本的 `--fifo` 参数虽然存在，但当前代码没有使用它。不要与旧 Y4M FIFO 补丁混用。

## 10. 当前短时联调顺序

以下是恢复运行后的操作参考，不表示本文编写时 Docker 一定可用。

### 10.1 先确认环境和接收端

在接收侧 WSL 执行：

```bash
docker info
docker ps --filter name=pandia-stridefix-rx-v2
ss -ltn 'sport = :9999'
```

若提示 WSL 中 Docker 不可用，先检查 Docker Desktop 是否运行及 Ubuntu-24.04 的 WSL Integration。此时不要继续启动实验，也不要把它误判为 WebRTC 故障。

若需要独立验证 GUI：

```bash
/usr/bin/ffplay -f lavfi -i 'testsrc2=size=640x360:rate=15' \
  -window_title 'WSLg display test'
```

完成后关闭测试图案。过去“任务栏有图标但窗口不可见 / WARN: COPY MODE”属于 WSLg 图形问题，和 YUV stride 花屏是两件事。

### 10.2 先确认输入目录没有需要跳过的历史帧

```bash
run_dir='/home/luo_k/pandia-stridefix-LIoZAovC'
find "$run_dir/frames" -maxdepth 1 -name '*.yuv' | wc -l
```

如果已有帧，原脚本会补播。不要直接把播放结果作为新一轮实时验收；先停止双方相关读写，归档旧帧文件或另安排本轮空输入目录，并核对容器映射。不要删除仍被挂载的目录本身。

### 10.3 显示就绪后立即启动 Sender

只在上述输入目录条件满足时，在接收侧 WSL 执行：

```bash
run_dir='/home/luo_k/pandia-stridefix-LIoZAovC'
preview_dir="$(mktemp -d "$run_dir/preview-XXXXXXXX")"
set -o pipefail
python3 -u "$HOME/pandia-camera-test/scripts/camera_external_recorder.py" \
  --input-dir "$run_dir/frames" \
  --raw-output "$preview_dir/received.yuv" \
  --mp4-output "$preview_dir/received.mp4" \
  --width 960 --height 540 --fps 15 \
  --duration 120 --idle-timeout 10 \
  2>&1 | tee "$preview_dir/recorder.log"
```

随后对方使用第 4.2 节命令启动摄像头 Sender。显示宽高必须跟本轮 `I420 export` 日志一致，不一致时先停止显示再调整。

短测发送约 20～30 秒即可。先停止 Sender，等待脚本闲置退出；脚本收集结束后才调用 FFmpeg，将已保存 raw 重新编码为 H.264 MP4。MP4 是接收后的再次编码，不是直接保存原始网络码流。

### 10.4 分层检查

```bash
docker logs --since 30s -f pandia-stridefix-rx-v2 2>&1 \
  | grep --line-buffered -E 'Sender connected|Received .*bytes|Frame received|Notify frame decoded|I420 export|[Ff]ailed'
```

另一个 WSL 终端：

```bash
find /home/luo_k/pandia-stridefix-LIoZAovC/frames \
  -maxdepth 1 -name '*.yuv' | wc -l
pgrep -af '[c]amera_external_recorder.py|[f]fplay'
```

不要在活动会话中反复用 TCP 连接探测工具连接 9999。当前 binary 的连接处理会替换已有信令 socket；端口检查优先用本机 `ss`，远端连通性探测安排在正式会话之前。

## 11. 常见故障应定位在哪一层

| 现象 | 优先检查 | 不能直接下的结论 |
| --- | --- | --- |
| 没有 Camera frame captured | USB 接入、V4L2 格式、摄像头占用 | 接收容器一定有问题 |
| TCP 连上但没有媒体 | Offer/Answer、信令版本、ICE、媒体路径、防火墙 | TCP 成功就证明视频成功 |
| 有解码日志，无 YUV 文件 | 导出失败、dump_path、挂载、权限、磁盘空间 | ffplay 坏了 |
| errno=2，容器目录失效 | 挂载目录是否被删除重建 | 修改分辨率即可解决 |
| 重启时报内部 bind-mount 不存在 | 保留旧容器诊断，使用有效路径重新创建 | 必須重装 WebRTC |
| YUV 有增长，脚本计数为 0 | 脚本是否存活、实际 input-dir、单帧长度 | 网络没有传过来 |
| 有周期横条和绿带 | 真实宽高、像素格式、stride 导出、单帧 PNG | 必然是网络丢包 |
| 任务栏有窗口但打不开 | 独立图案测试、WSLg 状态 | 必然是视频内容问题 |
| 重启播放固定片段后退出 | 历史帧、duration、idle-timeout | 当前仍在实时传输 |
| 延迟时大时小 | 采集、编码、网络、解码、导出、磁盘、队列、播放器分层计时 | 全是 GCC 或网络造成的 |

## 13. 下一步验收与优化

先保证每层都通过：摄像头有帧 → 信令与媒体连接成功 → 接收解码 → 正确导出 → 单帧清晰 → 连续显示 → 再测时延。

延迟可先用摄像头拍摄可见计时器并与实际画面比较；精确分层计时需记录采集、编码、收包、解码和呈现时间，跨机时间必须校准。不要把解码 ACK 延迟直接当作屏幕可见的端到端延迟。

后续预览建议脱离全量磁盘补播，采用带宽高、时间戳和独立序号的最新帧接口；录像另走独立路径。保存单帧文件和连续 raw 会重复占用空间：960×540、30 帧/秒时，一份 raw 约 23.3 MB/s，两份约 46.7 MB/s，尚未计算 MP4 和日志。

本阶段总结：**网络负责把编码视频送达，WebRTC 负责还原视频帧，导出补丁负责把内存像素正确交出来，Python 和 FFplay 负责把像素变成窗口。每一层成功都需要自己的证据。**
