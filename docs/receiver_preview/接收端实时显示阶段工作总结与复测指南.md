本阶段不引入 Pandia FPS Action、带宽预测模型、网络 trace 或 tc；不以修改拥塞控制算法解决显示问题。补丁本身不修改 RTP、ICE、信令或 GCC。

## 2. 实现架构

```text
对方电脑：sender → 编码 → RTP/UDP
                            │ 网络
本机 receiver 容器：收包 → 帧重组 → 视频解码
                                      ↓
                              VideoRenderer::OnFrame
                                      ↓
                              I420 / 缩放为 640×360
                                      ↓
                              单个待输出帧 + 后台写线程
                                      ↓
                              Y4M 命名管道（FIFO）
                                      ↓
本机 WSL：                         ffplay → 显示窗口
```

ffplay 不直接接收 WebRTC 网络包，也不负责 WebRTC 的 RTP 重组或 H.264 解码。它读取的是接收端已经解码好的像素流。

显示管道是本机进程间接口，不需要对方新增网络端口，也不是另一条跨机器视频连接。媒体源文件放在发送端，接收端不需要保存同一份源视频。

## 3. 源码排查与补丁内容

### 3.1 原有源码的问题

服务器源码路径为 `~/webrtc-pandia/src`，此前确认的提交为：

### 3.3 解码帧如何进入补丁

renderer 使用 `AddOrUpdateSink` 注册到视频轨道。轨道交付解码画面时调用 `OnFrame`。本补丁仅对名为 `remote` 的 renderer 启用输出，不把本地预览轨道当作远端画面。

每个画面的处理过程：

1. `ToI420()` 获取 I420 图像。
2. 若尺寸不同于 640×360，用 `I420Buffer::Create` 和 `ScaleFrom` 真正缩放像素。
3. 按各平面的实际 stride 逐行复制，形成紧凑排列的 Y、U、V 数据。
4. 将最新一帧交给后台输出线程。

固定 640×360 只改变本地预览尺寸，不锁定发送端分辨率或码率。低分辨率帧放大不会恢复已经损失的细节。

### 3.4 队列和管道设计

- 只保留一个尚未开始输出的待写帧，新帧可替换旧待写帧，限制补丁自身的排队。
- 已开始写入的帧处理部分写入与重试，避免随意丢弃半帧造成数据错位。
- 管道写操作在后台线程，图像转换、缩放和复制仍在 `OnFrame` 中，有 CPU 开销。
- 没有播放器读端时，不阻塞接收回调等待播放器；对应预览帧可以被丢弃。
- 后台线程屏蔽 SIGPIPE 并处理断管，避免关闭播放器直接终止接收进程。
- 断管后设计上可等待新的读端；该恢复路径仍应实测。

注意：一个待写帧不代表整个显示链路只有一帧缓存，管道、当前写入帧及 ffplay 内部仍可能存在缓冲。

### 3.5 输出格式和配置

环境变量：

| 名称 | 含义 |
| --- | --- |
| `PANDIA_FRAME_FIFO` | 容器内已存在的 FIFO 路径，用于开启实时输出 |
| `PANDIA_PREVIEW_FPS` | Y4M 标称帧率，默认 25，接受 1～120 的整数 |

数据格式为 Y4M：先写文件头，再逐帧写入 `FRAME` 标记和 I420 像素。

```text
YUV4MPEG2 W640 H360 F25:1 Ip A0:0 C420jpeg
FRAME
<第一帧像素数据>
FRAME
<第二帧像素数据>
```

`PANDIA_PREVIEW_FPS=25` 不是实际收到 25 fps 的证明，也不控制发送端帧率。当前接口没有传递完整的真实采集时间戳，不可直接用播放器时间轴计算 G2G 延迟。

## 4. 关键问题及处理方法

### 4.1 初版窗口约 5 秒后关闭，但接收容器仍运行

当时接收日志仍持续出现 `Frame received`、`Notify frame decoded`。已检查的发送日志出现从 320×180 到 480×270 的尺寸变化，间隔约 3.88 秒，后续还有更高分辨率。

初版输出在源尺寸变化时关闭 FIFO，ffplay 使用 `-autoexit`，读到流结束后正常退出。因此“没有明显报错”与“容器仍在运行”可以同时发生。

解决方法：v2 将所有输出画面实际缩放到 640×360，保持 Y4M 流尺寸恒定；不是仅改头部尺寸，也不是通过关闭 GCC 强行固定网络侧分辨率。

### 4.2 在 receiver.log 中搜不到 Preview

自定义 WebRTC 文件日志不保证包含所有 RTC_INFO 或控制台输出。v2 将关键预览事件直接写入 stderr，并在启动命令中用 `tee` 保存到 `receiver-console.log`。

日志分工：

- `receiver.log`：WebRTC 收包、帧接收、解码等事件。
- `receiver-console.log`：容器启动及预览连接、尺寸切换等控制台诊断。

### 4.3 视频不断循环，不等于显示功能异常

当前文件视频源在实验中会循环使用。源片段长度与整个实验持续时间不同；5 秒素材可以用于一分钟收发测试。

之前的 720p I420 素材为 103,680,000 字节，等于 75 帧；按 25 fps 是 3 秒。新裁剪素材为 125 帧，按 25 fps 是 5 秒。

### 4.4 YUV 文件很大

原始 I420 没有 H.264 那样的压缩。1280×720 每帧需要：

```text
1280 × 720 × 1.5 = 1,382,400 字节
5 秒 × 25 帧/秒 × 1,382,400 = 172,800,000 字节
```

该文件是发送端的原始输入，不表示网络直接按原始 YUV 大小发送；网络发送的是编码后的数据。

### 4.5 最新“warn：copy mode 打不开”反馈

目前只有用户对提示的描述，没有完整错误文字、截图及对应日志。尚不能判断来自 ffplay、终端、WSL 图形显示还是其他组件，也不能认定补丁需要修改。

先保留现场，检查进程、解码日志、预览连接日志；不要同时让两个 ffplay 读取同一个 FIFO，以免分走数据并造成格式异常。具体诊断命令见第 8 节。

| 有解码但没有预览回调事件 | 是否运行 v2、远端 sink 注册及控制台日志 |
| 有 source 事件但没有 ffplay connected | 播放器读端、FIFO 类型/权限、两端是否共享同一个管道 |
| 已连接但窗口无画面或告警 | ffplay 完整输出、WSL 图形环境、像素流完整性 |
| 仍出现旧版 resolution changed | 是否使用旧二进制或旧入口 |

Docker Desktop 下不能只凭路径名称相同就断定双方共享了同一个 FIFO，必须以实际连接和画面输出验证。排查前不要额外启动第二个读同一 FIFO 的 ffplay。

## 9. 阶段结论与后续工作

本阶段已实现一个接收端应用层显示接口：在既有 WebRTC 解码能力之后，增加固定尺寸像素输出，通过本地 FIFO 交给 ffplay。无需为显示功能同步修改 sender，也不需要更改网络传输协议。

当前还不能宣称“新版双机实时显示已完全稳定”。下一步先收集当前告警的完整证据并解决显示问题，然后完成双机一分钟基线、尺寸变化和播放器重连测试，再考虑摄像头和弱网长时间运行。

现阶段限制：无音频播放、预览固定 640×360、非 16:9 输入会被补丁拉伸、未处理旋转元数据、使用标称帧率而非完整实时戳。后续若要求精确实时同步、G2G 测量或 MLLM 消费帧，应另行设计带时间戳的接口和统计机制。
